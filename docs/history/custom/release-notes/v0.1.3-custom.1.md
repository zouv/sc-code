# v0.1.3-custom.1

**基于上游**：Sidenai/sidex `main@ad978652`（v0.1.3-dev）

> 本仓库首个自定义发布（首个 `v*-custom.*` tag）。产物为**本地打包的 Windows 安装包**（上游 sidex 不发布预编译二进制），含 MSI + NSIS 两种格式。

## 自定义改动

本轮汇总自 `CUSTOMIZATIONS/registry.md`（账本为唯一权威来源）：

### 新功能：从本地 VSIX 安装扩展（CUSTOM-20261013-001）

上游 sidex 的 VSIX 安装链路在本项目里整体是断的（详见下方"上游问题修复"），本版本把它接上了：

- 四个入口：**命令面板**、**扩展视图标题「...」菜单**、**资源管理器右键 `.vsix`**、**把 `.vsix` 拖进窗口**
- 流程：原生文件选择框（Tauri dialog）→ Tauri 侧解压到 `%APPDATA%\SideX\extensions\<publisher>.<name>` → 写入扩展视图的已安装记录 → 走既有热加载逻辑自动加载并激活
- 卸载沿用原链路（扩展视图卸载 → 删除磁盘目录）
- 实现放在 `CUSTOMIZATIONS/src/vsix-install/`，仅在上游 `src/main.ts` 加了一行挂载导入

### 上游问题修复（CUSTOM-20261013-002）

- **修复**：Tauri 下 `file://` 被 `FileAccess.uriToBrowserUri()` 改写成 `sidex-asset://`，而该 scheme 只有 Tauri 网络层协议、`IFileService` 无对应 provider，导致任何"通过扩展资源加载服务读磁盘扩展文件"的路径必然失败（现象：安装 VSIX 时报 `Cannot find a valid extension from the location file:///...`）。现改为 Tauri + `file://` 直接走 `IFileService`

### 打包 / 开发体验（CUSTOM-20261012-002 / 004 / 005）

- 自定义版本号四处同步机制（含 MSI 专用的纯数字 `wix.version`）
- 新增快捷命令 `npm run dev:custom` / `npm run build:custom`（内置 `AWS_LC_SYS_PREBUILT_NASM=1`，规避 `aws-lc-sys` 缺 NASM 的编译中断），以及 `CUSTOMIZATIONS/scripts/dev.bat` / `build.bat` 包装
- 新增 `CUSTOMIZATIONS/docs/commands.md`（常用命令速查）、`docs/pitfalls.md`（历史坑点库）、`architecture.md`（代码链路图谱）

### 自定义开发机制

- `CUSTOMIZATIONS/` 全套：规则（README）、改动账本（registry）、代码地图（architecture）、坑点库、`[CUSTOM-BEGIN]` 标记约定、`check-registry.sh` 一致性自检
- `.agents/skills/`：`sidex-record-change` / `sidex-merge-upstream` / `sidex-release` / `sidex-publish`

## 上游同步

- 无（本版本基于首次引入的 vendor 基线 `main@ad978652`，尚未合并后续上游提交）

## 已知限制

- 仅 Windows 产物（在 Windows 上打包）；macOS / Linux 需在对应平台自行打包
- 从 VSIX 安装的扩展，其"平台兼容性校验"仍沿用上游 web 模式的宽松策略（Tauri 下不拦截非 web 扩展）
- 上游 issue #102（扩展平台检测导致下错架构的二进制，如 Claude Code 装成 alpine-arm64）**未修复**，属于上游遗留问题
